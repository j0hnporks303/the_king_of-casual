III

Opening APFS on Linux

Linux has no native APFS support. What it has instead is four independent reimplementations, written by different people, with different blind spots, none of which is complete. Knowing which one to reach for — and where each one quietly lies to you — is the single most useful thing in this manual.

6The four access engines

Every APFS technique in this manual runs on top of one of four independent implementations. They are not interchangeable. Learn the shape of each.

6.1 libyal libfsapfs — the forensic reference

Joachim Metz's library, part of the libyal family that also gives you libewf. It is read-only by design, exposes container and volume metadata in exhaustive detail, handles FileVault with a password or recovery key, and — crucially — is the APFS backend that plaso uses through dfVFS. If your timeline tooling can see a file, it is usually seeing it through this library.

StrengthsMetadata depth, encryption support, snapshot enumeration, stable behaviour, integrates with plaso WeaknessesSlower on large trees; FUSE mount is single-threaded; less forgiving of damaged containers Binariesfsapfsinfo (inspect), fsapfsmount (FUSE mount) Use it forGround truth about the container, encrypted volumes, and anything feeding plaso

6.2 apfs-fuse — the practical workhorse

Simon Gander's implementation. Read-only FUSE, fast, tolerant, and the best of the four at the things you actually spend your day doing: transparent decmpfs/LZFSE decompression, extended attributes, and mounting individual snapshots by name.

StrengthsSpeed, compression handling, xattrs, snapshot mounting, FileVault support, copes with odd containers WeaknessesLess metadata introspection than libfsapfs; occasional divergence on exotic records Binariesapfs-fuse, apfsutil Use it forDay-to-day file access, snapshot work, anything involving compressed files

6.3 linux-apfs-oot — the kernel module

Ernesto A. Fernández's out-of-tree kernel driver, with its companion apfsprogs (apfsck, apfs-snap, apfs-label). Being a real kernel filesystem it is dramatically faster than FUSE and works with tools that dislike FUSE mounts. It is also the only one that can write.

StrengthsKernel speed, real mount semantics, apfsck structural verification, snapshot mounting WeaknessesNo FileVault support at all. Write support is experimental. Needs DKMS against your running kernel. Use it forFast bulk access to unencrypted volumes, and structural integrity checking
■ CAUTION — THE MODULE CAN WRITE

This is the one engine capable of modifying evidence. Mount it ro explicitly, always, and if you have any reason to exercise its write path, do it against the copy-on-write overlay from §4.3 and never against the image.

6.4 The Sleuth Kit — pool-aware, classically shaped

TSK gained APFS support through its pool abstraction: an APFS container is a pool, and the volumes inside it are addressed by a pool volume block. This buys you the entire classical toolchain — fls, istat, icat, tsk_recover, body files for mactime — against APFS.

StrengthsThe whole traditional workflow; inode-level addressing; body-file timelines; Autopsy integration WeaknessesCommand-line encrypted-volume handling is inconsistent between builds; no snapshot support; unallocated-space semantics do not map cleanly onto copy-on-write Use it forTimelines, inode-level work, deleted-entry recovery on unencrypted volumes
▲ DEVIL — THE ENCRYPTION / BLOCK-LEVEL DEADLOCK

This is the defining constraint of your case and it is worth internalising now. There is no reliable tool on Linux that decrypts a FileVault APFS volume back out to a flat raw image. apfs-fuse and fsapfsmount decrypt on the fly, at the file level, and present you a filesystem. They do not hand you a decrypted block device.

The consequence: for your encrypted Data volume you get excellent file-level access, but block-level techniques — TSK inode walks, blkls unallocated extraction, raw carving of free space — either do not work or must be run through the FUSE mount, where they see only allocated files. Plan the examination around this. The unencrypted volumes (Preboot, Recovery, and on many systems the sealed System volume) remain fully available to block-level tooling, which is one reason §49 matters more than its size suggests.

7Building the toolchain on Parrot

None of the four are packaged. All four build cleanly on current Debian/Parrot. Do these once, record the commit hashes, and move on.

7.1 Prerequisites

apt install -y build-essential cmake git pkg-config autoconf automake libtool \
    libfuse3-dev fuse3 libbz2-dev zlib1g-dev libssl-dev libattr1-dev \
    python3-dev python3-pip flex bison dkms linux-headers-$(uname -r)

7.2 apfs-fuse

git clone https://github.com/sgan81/apfs-fuse.git ~/tools/apfs-fuse
cd ~/tools/apfs-fuse && git submodule update --init   # pulls the bundled lzfse
mkdir build && cd build
cmake .. -DUSE_FUSE3=ON && make -j$(nproc)
make install && ldconfig

# record what you built — this goes in the case notes
git -C ~/tools/apfs-fuse rev-parse --short HEAD
apfs-fuse --help | head -20

7.3 libyal libfsapfs

git clone https://github.com/libyal/libfsapfs.git ~/tools/libfsapfs
cd ~/tools/libfsapfs
./synclibs.sh          # fetches the sibling libyal dependencies
./autogen.sh
./configure --enable-python --with-libfuse
make -j$(nproc)
make install && ldconfig

fsapfsinfo -V
fsapfsinfo 20240508
▸ TIP — THE PYTHON BINDINGS ARE THE REAL PRIZE

--enable-python builds pyfsapfs, which lets you walk the container programmatically instead of scraping CLI output. Nearly every custom script in §62 and the exotic techniques in Part IX are far easier through it.

python3 -c "import pyfsapfs; print(pyfsapfs.get_version())"
20240508

7.4 The kernel module and apfsprogs

# --- out-of-tree read/write driver ---
git clone https://github.com/linux-apfs/linux-apfs-oot.git ~/tools/linux-apfs-oot
cd ~/tools/linux-apfs-oot && make -j$(nproc)
make install && depmod -a && modprobe apfs
lsmod | grep apfs
apfs                  282624  0

# --- apfsck / apfs-snap / apfs-label ---
git clone https://github.com/linux-apfs/apfsprogs.git ~/tools/apfsprogs
cd ~/tools/apfsprogs/apfsck && make -j$(nproc) && sudo make install
cd ../apfs-snap && make -j$(nproc) && sudo make install
cd ../apfs-label && make -j$(nproc) && sudo make install
● NOTE — DKMS SO IT SURVIVES KERNEL UPDATES

A rolling distribution will update your kernel and silently break the module. Register it with DKMS so it rebuilds automatically, or you will one day find your mount command failing mid-case for no apparent reason.

7.5 The Sleuth Kit with pool support

Parrot's packaged sleuthkit is generally recent enough. Confirm APFS is compiled in before trusting it — a build without pool support fails in confusing ways rather than saying so.

fls -V; pstat -V 2>/dev/null || echo "no pool support — build from source"
The Sleuth Kit ver 4.12.1

9FileVault2 — keybags, wrapped keys, unlocking

You have the password. This section explains what that password actually unlocks, because the chain has four links and knowing them tells you what can go wrong and what else is recoverable.

9.1 The key hierarchy

   user password  or  personal recovery key
          │
          │  PBKDF2-HMAC-SHA256, iteration count and salt
          │  stored in the KEK blob itself
          ▼
   derived key ──── RFC 3394 AES key unwrap ────▶ KEK  (key encryption key)
                                                    │
                                                    │  RFC 3394 unwrap
                                                    ▼
                                                  VEK  (volume encryption key)
                                                    │
                                                    │  AES-XTS, tweak = block address
                                                    ▼
                                            plaintext file data

  Where these live:
    nx_superblock.nx_keylocker ──▶ container keybag   (AES-XTS, key = container UUID)
        ├─ KB_TAG_VOLUME_KEY            per volume: the wrapped VEK
        └─ KB_TAG_VOLUME_UNLOCK_RECORDS per volume: where its volume keybag lives
                                          │
                                          ▼
                                    volume keybag       (AES-XTS, key = volume UUID)
        ├─ KB_TAG_VOLUME_UNLOCK_RECORDS  one wrapped KEK per crypto-user
        └─ KB_TAG_VOLUME_PASSPHRASE_HINT the password hint, in cleartext
▲ DEVIL — THE KEYBAGS ARE "ENCRYPTED" WITH PUBLIC INFORMATION

Both keybags are encrypted with AES-XTS using the container UUID and the volume UUID respectively — values that sit in cleartext in the superblocks a few hundred bytes away. This is obfuscation, not security, and it is deliberate: it lets the boot process locate unlock records before any secret is known. For you it means the keybag structure is fully readable without the password. You can enumerate how many crypto-users exist, read the password hint, and see whether an institutional or personal recovery key was enrolled — all before authenticating. That is real intelligence about the account even in the case where you never get the password.

9.2 Unlocking with libfsapfs

# inspect first: which volume is encrypted, and does it take our password
fsapfsinfo -o 524308480 -p 'TheUserPassword' -f 5 /evidence/mbp-001.dd

# mount every volume the password opens, read-only, under /mnt/apfs
mkdir -p /mnt/apfs
fsapfsmount -o 524308480 -p 'TheUserPassword' /evidence/mbp-001.dd /mnt/apfs

ls /mnt/apfs/
apfs1  apfs2  apfs3  apfs4  apfs5      # one directory per volume, in container order
ls /mnt/apfs/apfs5/
Applications  Library  System  Users  private  usr  ...
-o <bytes>byte offset of the container (sector × 512) -p <pw>user password -r <key>personal recovery key, the 24-character dashed string, if you have that instead -f <n>restrict to one volume by index -X allow_otherlet other users (and root-run tools) see the mount

9.3 Unlocking with apfs-fuse

# attach the image as a read-only loop device first
LOOP=$(losetup --read-only --partscan --find --show /evidence/mbp-001.dd)

# list volumes and their indices
apfs-fuse -l ${LOOP}p2

# mount volume 4 (0-indexed — the Data volume) with the password
apfs-fuse -v 4 -p 'TheUserPassword' -o ro,allow_other ${LOOP}p2 /mnt/data

ls /mnt/data/Users/
Shared  jdoe

# unmount cleanly when done
fusermount3 -u /mnt/data
■ CAUTION — PASSWORDS ON THE COMMAND LINE

-p 'password' puts the subject's credential into your shell history, into your script session log, and into /proc where any local process can read it while the command runs. On a shared or monitored analysis box this is a genuine disclosure. Prefer an interactive prompt where the tool offers one, and if you must pass it inline, prefix the command with a space so HISTCONTROL=ignorespace keeps it out of history — and remember to scrub the session transcript before it becomes an exhibit.

9.4 If you did not have the password

Out of scope for your case, but worth a paragraph because it explains the shape of the problem. The wrapped KEK blob — salt, iteration count, and the wrapped key — is extractable from the volume keybag without authenticating, and is a legitimate offline attack target. hashcat mode 18300 ("Apple File System / APFS") consumes exactly that structure. The extraction is done by apfs2hashcat.py, distributed with hashcat's tools.

The practical reality is that PBKDF2 iteration counts on modern macOS make this viable only against weak or known-pattern passwords. Where it does pay off is with the personal recovery key, whose format is fixed and whose keyspace, while large, is structured.

9.5 Confirming you are actually decrypted

A silently-failed unlock can present as an empty or nonsensical filesystem rather than an error. Check positively:

# a known-plaintext file that exists on every macOS install
file /mnt/apfs/apfs5/private/var/log/install.log
/mnt/apfs/apfs5/private/var/log/install.log: ASCII text

# and the system version, which also tells you exactly which OS you are dealing with
plistutil -i /mnt/apfs/apfs1/System/Library/CoreServices/SystemVersion.plist -o - | \
    grep -A1 'ProductVersion\|ProductBuildVersion'
<key>ProductBuildVersion</key>   <string>23H124</string>
<key>ProductVersion</key>        <string>14.7.1</string>
▸ TIP — PIN THE OS VERSION BEFORE ANYTHING ELSE

Read SystemVersion.plist as the first thing you do after mounting, and write the build number at the top of your notes. Half the artifact paths in Part VII moved between releases. Every version tag in this manual is meaningless until you know which number you are holding.

10.1 Gotchas worth knowing before they cost you a day

▲ DEVIL — FUSE MOUNTS HIDE THE FILESYSTEM FROM YOUR TOOLS

A FUSE mount presents files. It does not present a block device, inode numbers you can trust across tools, or unallocated space. Anything in Part V that addresses the filesystem structurally — fls, istat, blkls, tsk_recover — must run against the image, not against /mnt/apfs. Running fls on a FUSE mountpoint will either error or silently describe your own Linux filesystem instead. This mistake is common and produces findings that are quietly, completely wrong.

▲ DEVIL — THE ENGINES DISAGREE, AND THAT IS DATA

When apfs-fuse and fsapfsinfo report different things about the same object — a different size, a file one sees and the other does not, a differing timestamp — do not simply pick the one you like. Divergence usually means one of three things: a genuine parser bug, a structurally unusual record (an oversized xattr, a clone, a sparse extent), or deliberate manipulation designed to confuse parsers. Record the disagreement and investigate it. In several published cases the discrepancy was the finding.

● NOTE — CASE SENSITIVITY

The Data volume on macOS is case-insensitive but case-preserving. Your Linux filesystem is case-sensitive. Two files that cannot coexist on macOS can coexist in your extraction directory, and a script that assumes Library and library are distinct will behave differently on the mount than the Mac did. When matching paths, compare case-insensitively.

● NOTE — NORMALISATION

APFS stores filenames as UTF-8 and, unlike HFS+, does not normalise them — but it does hash them case-insensitively for lookup on case-insensitive volumes. The upshot: two filenames that look identical on screen can differ in byte representation (precomposed vs decomposed accents). When grepping for a filename containing non-ASCII characters, search for both normalisation forms or you will miss it.

python3 -c "import unicodedata as u; n='café.txt'; \
print(repr(u.normalize('NFC',n)), repr(u.normalize('NFD',n)))"
'café.txt' 'café.txt'
