41Checkpoint time-travel

The checkpoint descriptor area holds superseded container superblocks — complete roots of the filesystem as it existed at earlier transactions. Because APFS is copy-on-write, the trees those roots point at are frequently still intact on disk. Reconstructing one gives you the entire filesystem as it was, with names, paths and metadata, for a moment nobody chose to snapshot.

41.1 Parsing the container superblock

Field offsets, all little-endian, from the start of the block:

OffsetSizeFieldMeaning
0x008o_cksumFletcher-64 over bytes 8..end
0x088o_oidObject id
0x108o_xidTransaction id — how you order checkpoints
0x184o_typeObject type
0x204nx_magic'NXSB' = 4E 58 53 42
0x244nx_block_sizeUsually 4096
0x288nx_block_countContainer size in blocks
0x608nx_next_xidNext transaction to be issued
0x684nx_xp_desc_blocksSize of the descriptor ring
0x708nx_xp_desc_baseBlock address of the descriptor area
0x788nx_xp_data_baseBlock address of the data area
0x988nx_spaceman_oidSpace manager — §45
0xA08nx_omap_oidContainer object map
0xB8800nx_fs_oid[100]Volume superblock object ids
 
cat > ~/cases/001/06-analysis/nxsb_scan.py <<'PY'
#!/usr/bin/env python3
"""Enumerate every valid container superblock in the checkpoint descriptor area."""
import struct, sys

IMG   = sys.argv[1]
START = int(sys.argv[2])        # container byte offset, from mmls
BS    = 4096

def fletcher64(data):
    """APFS variant: computed over the object excluding the 8-byte checksum."""
    lo = hi = 0
    for i in range(0, len(data), 4):
        lo = (lo + int.from_bytes(data[i:i+4], 'little')) % 0xFFFFFFFF
        hi = (hi + lo) % 0xFFFFFFFF
    c1 = (0xFFFFFFFF - ((lo + hi) % 0xFFFFFFFF))
    c2 = (0xFFFFFFFF - ((lo + c1) % 0xFFFFFFFF))
    return (c2 << 32) | c1

with open(IMG, 'rb') as f:
    f.seek(START)
    blk0 = f.read(BS)
    assert blk0[0x20:0x24] == b'NXSB', 'not an APFS container at that offset'
    desc_base   = struct.unpack_from('<Q', blk0, 0x70)[0]
    desc_blocks = struct.unpack_from('<I', blk0, 0x68)[0] & 0x7FFFFFFF
    print(f'descriptor area: block {desc_base}, {desc_blocks} blocks\n')

    found = []
    for i in range(desc_blocks):
        f.seek(START + (desc_base + i) * BS)
        b = f.read(BS)
        if b[0x20:0x24] != b'NXSB':
            continue
        xid    = struct.unpack_from('<Q', b, 0x10)[0]
        stored = struct.unpack_from('<Q', b, 0x00)[0]
        valid  = fletcher64(b[8:]) == stored
        found.append((xid, desc_base + i, valid))

for xid, blk, ok in sorted(found):
    print(f'xid {xid:12d}  block {blk:8d}  checksum {"OK" if ok else "BAD"}')
print(f'\n{len(found)} checkpoints recoverable')
PY

41.2 Mounting an earlier checkpoint

Writing a full B-tree walker for an arbitrary checkpoint is a project. There is a much cheaper route that gets you a mountable filesystem: make an older checkpoint the newest one, on a copy-on-write overlay, and let the existing tools do the work.

■ CAUTION — OVERLAY ONLY, NEVER THE IMAGE

This technique writes to the container. It must be performed against the device-mapper overlay from §4.3. Verify with lsblk that you are pointed at /dev/mapper/evid-cow before any dd, and re-verify the master hash afterwards.

# 1. build the COW overlay (see §4.3) and confirm the target
lsblk /dev/mapper/evid-cow

# 2. neutralise every checkpoint newer than the one you want, by corrupting
#   their magic so the mounter skips them. Here: keep xid 214402 at block 201.
for blk in 208 216; do
     printf 'XXXX' | dd of=/dev/mapper/evid-cow bs=1 \
        seek=$((524308480 + blk*4096 + 0x20)) conv=notrunc
   done

# 3. copy the chosen older superblock over block 0 as well
dd if=/dev/mapper/evid-cow of=/tmp/old-nxsb.bin bs=4096 \
      skip=$(( (524308480/4096) + 201 )) count=1
dd if=/tmp/old-nxsb.bin of=/dev/mapper/evid-cow bs=4096 \
      seek=$(( 524308480/4096 )) count=1 conv=notrunc

# 4. mount normally — you are now looking at the filesystem at xid 214402
apfs-fuse -v 4 -p 'PW' -o ro /dev/mapper/evid-cow /mnt/past
ls -la /mnt/past/Users/jdoe/Downloads/

# 5. tear down and prove the master is untouched
fusermount3 -u /mnt/past; dmsetup remove evid-cow
sha256sum -c /evidence/mbp-001.dd.sha256
▲ DEVIL — WHAT THIS BUYS YOU, AND WHAT IT DOES NOT

Buys you: the complete filesystem — paths, names, timestamps, contents — at a moment in the recent past that no snapshot covers. Checkpoints are written constantly, so the window is typically minutes to hours before acquisition. If a file was deleted an hour before the machine was seized, this is frequently the only way to get it back with its metadata intact.

Does not buy you: anything whose blocks have been reallocated since. Older checkpoints degrade — the oldest entries in the ring will often fail to mount because their trees have been partly overwritten. Work newest-to-oldest and expect a cliff. Also note the descriptor ring is small: this is a window of hours, not weeks. For weeks, you need snapshots.

42Snapshot archaeology

Snapshots are the single highest-yield artifact on APFS, and the one most likely to defeat an adversary's cleanup entirely.

42.1 Enumerate everything, on every volume

for v in 1 2 3 4 5; do
    echo "=== volume $v"
    fsapfsinfo -o 524308480 -p 'PW' -f $v -s /evidence/mbp-001.dd 2>/dev/null | \
        grep -E 'Name|XID|Time'
  done

42.2 Mount them all and sweep each

SNAPS=$(fsapfsinfo -o 524308480 -p 'PW' -f 5 -s /evidence/mbp-001.dd | \
        awk '/Name/{print $3}')
i=0; for s in $SNAPS; do
     i=$((i+1)); mkdir -p /mnt/snap$i
     apfs-fuse -v 4 -p 'PW' -s "$s" -o ro /dev/loop0p2 /mnt/snap$i
     echo "$i -> $s"
   done

# run the §40 persistence sweep inside each, and hash the results
for m in /mnt/snap*; do
     find $m/Library/LaunchDaemons $m/Library/LaunchAgents \
          $m/Users/*/Library/LaunchAgents -name '*.plist' 2>/dev/null | \
       sed "s|$m||" | sort > ~/cases/001/06-analysis/persist-$(basename $m).txt
   done

# the diff between the oldest snapshot and the live volume is the cleanup
diff ~/cases/001/06-analysis/persist-snap1.txt \
      ~/cases/001/06-analysis/persist-live.txt
< /Users/jdoe/Library/LaunchAgents/com.apple.softwareupdated.plist
▸ TIP — DIFF THE WHOLE TREE, NOT JUST PERSISTENCE

A full recursive diff between a snapshot and the live volume is the fastest way to see everything that changed in that interval — files added, modified and deleted, all at once.

diff -rq /mnt/snap1/Users /mnt/data/apfs5/Users 2>/dev/null | head -100
Only in /mnt/snap1/Users/jdoe/Downloads: installer.pkg
Files /mnt/snap1/Users/jdoe/.zsh_history and /mnt/data/.../\
.zsh_history differ

That second line is worth pausing on: the shell history was modified between the snapshot and acquisition. The snapshot holds the version before it was edited.

42.3 Detecting deleted snapshots

An adversary who understands APFS will delete the snapshots. That deletion is itself detectable.

  • Cadence gaps. Time Machine local snapshots are created hourly and named with their timestamp. Sort the names; a missing hour in an otherwise unbroken hourly series, on a machine that was powered on through that hour (confirm via unified log or powerlog), means a snapshot was removed.
  • XID gaps. Snapshot XIDs advance with the container. A large XID jump between consecutive surviving snapshots indicates transactions — and probably snapshots — in between.
  • Orphaned snapshot metadata. Deletion removes the snapshot's records from the snapshot metadata tree, but the extents it pinned may not be immediately reclaimed. Blocks referenced by no live object and no surviving snapshot are the remains (§45).
  • The unified log records it. Snapshot creation and deletion are logged. Grep the parsed unified log for snapshot, APFSSnapshot, tmutil, localsnapshot, deletelocalsnapshots.
grep -iE 'snapshot|localsnapshot|tmutil' ~/cases/001/04-timeline/unifiedlog.csv | \
    grep -iE 'delet|destroy|remov' | head -30

43XID and inode anomaly detection

The most reliable anti-timestomping technique available on APFS, and it requires nothing but metadata you already have.

43.1 The principle

Inode object identifiers are allocated sequentially from the volume superblock's apfs_next_obj_id counter. Every new file gets the next number. Therefore object id order is creation order — a fact no user-space tool can alter, because the counter is filesystem state, not file metadata.

   Normal volume:  object id ▲ correlates with creation time ▲

   obj_id  2100000 ─────────────────────────────────── 2026-07-30  ✓
   obj_id  2100001 ─────────────────────────────────── 2026-07-30  ✓
   obj_id  2100002 ─────────────────────────────────── 2019-03-14  ✗  ← impossible
   obj_id  2100003 ─────────────────────────────────── 2026-07-30  ✓

A file with a high object id and an old creation date was created recently and backdated. There is no benign explanation on a single volume: the counter only moves forward.

43.2 Detecting it

cat > ~/cases/001/06-analysis/xid_anomaly.py <<'PY'
#!/usr/bin/env python3
"""Flag files whose inode number is inconsistent with their creation time."""
import subprocess, re, sys, statistics

IMG, OFF, VOL = sys.argv[1], sys.argv[2], sys.argv[3]

# body file gives inode + crtime for every file in one pass
out = subprocess.run(['fls','-o',OFF,'-B',VOL,'-r','-m','/',IMG],
                     capture_output=True, text=True).stdout

rows = []
for line in out.splitlines():
    p = line.split('|')
    if len(p) < 11: continue
    try:
        inode  = int(p[2].split('-')[0])
        crtime = int(p[10])
    except ValueError:
        continue
    if crtime > 0:
        rows.append((inode, crtime, p[1]))

rows.sort()                       # by inode = by true creation order

# walk forward; creation time should be non-decreasing. Report inversions.
high_water = 0; anomalies = []
for inode, crtime, name in rows:
    if crtime < high_water - 86400:      # more than a day out of order
        anomalies.append((inode, crtime, high_water, name))
    high_water = max(high_water, crtime)

import datetime as dt
f = lambda t: dt.datetime.utcfromtimestamp(t).strftime('%Y-%m-%d %H:%M:%S')
print(f'{len(anomalies)} inode/timestamp inversions\n')
for inode, crtime, hw, name in anomalies[:60]:
    print(f'inode {inode:9d}  claims {f(crtime)}  '
          f'but neighbours are {f(hw)}\n    {name}')
PY

python3 ~/cases/001/06-analysis/xid_anomaly.py /evidence/mbp-001.dd 1024040 1276
3 inode/timestamp inversions

inode   2100002  claims 2019-03-14 09:12:00  but neighbours are 2026-07-30 02:38:44
    /data/Users/jdoe/Library/LaunchAgents/com.apple.softwareupdated.plist
■ CAUTION — LEGITIMATE INVERSIONS EXIST

Before reporting a backdated file, rule out the innocent explanations:

  • Restores. Migration Assistant, Time Machine restores and rsync -a recreate files with preserved original timestamps and fresh inode numbers. A restore produces thousands of inversions in one contiguous inode range — a distinctive, obviously benign pattern.
  • Archive extraction. tar -p, unzip and installers preserve stored timestamps.
  • Clock changes. If the system clock moved backwards, everything created afterwards inverts. Check the unified log for settimeofday first.

The finding is not "an inversion exists". It is "an isolated inversion, of a small number of files, in a persistence-relevant location, with no restore or clock event to explain it". That is what the output above shows: three anomalies, one of which is a launch agent.

43.3 Corroborating witnesses

Once you have a candidate, gather the independent evidence from §13.1 and §14:

WitnessWhat it should show for a stomped file
Inode number vs neighboursCreated recently, claims to be old
change_timeRecent — the moment the lie was written
write_generation_counterInconsistent with a file "untouched since 2019"
Containing directory's mod_timeDirectory was modified when the file was really created
FSEventsA creation event for that path, at the real time
Unified log / ExecPolicyFirst-execution record at the real time
SnapshotsFile absent from snapshots older than its claimed date

That last one is decisive and trivially checkable: a file claiming creation in 2019 that does not appear in a snapshot taken last week did not exist last week.

44Orphans, tombstones and dangling extents

44.1 The private directory

APFS reserves two well-known object ids: 2 is the volume root directory, 3 is the private directory. Files that were unlinked while still open by a process are moved into the private directory rather than deleted — they have no name in any directory, but their inode and data remain fully intact until the last handle closes.

▲ DEVIL — DELETED-BUT-OPEN FILES SURVIVE A DEAD-BOX SEIZURE

If the machine was powered off abruptly — pulled plug, forced shutdown, battery removal — every file that a running process had unlinked but still held open is sitting in the private directory, complete. Malware that deletes itself from disk at launch and keeps running does exactly this. So does a logging process whose log was deleted underneath it.

This is one of the few genuine advantages of an ungraceful shutdown, and almost nothing enumerates it automatically. Walk inodes whose parent_id is 3, or whose parent id resolves to no directory record at all.

python3 - <<'PY'
import pyfsapfs
v = pyfsapfs.volume()
c = pyfsapfs.container(); c.open('/evidence/mbp-001.dd')   # offset handling per your build
# walk the file entries and report any whose parent is the private directory
def walk(entry, path=''):
    try: sub = entry.number_of_sub_file_entries
    except Exception: return
    for i in range(sub):
        ch = entry.get_sub_file_entry(i)
        yield ch, path + '/' + (ch.name or '?')
        yield from walk(ch, path + '/' + (ch.name or '?'))
PY

# practical alternative: TSK lists allocated inodes with no directory entry
fls -o $OFF -B $DAT -r -p $IMG | awk '{print $2}' | sort -u > /tmp/named.txt
istat -o $OFF -B $DAT $IMG 3       # the private directory itself

44.2 Dangling extents

A FILE_EXTENT record maps a range of blocks to a file. When records are removed inconsistently — through corruption, interrupted deletion, or deliberate tampering — you get extents referencing blocks that no live inode claims. Those blocks hold real file content with no name attached.

# apfsck reports structural inconsistencies including orphaned records
apfsck -c /dev/mapper/evid-cow
# run against the OVERLAY: apfsck can be told to repair, and you never want that
# touching the evidence

45Free space and the space manager

On a copy-on-write filesystem, unreferenced blocks are where every superseded version of every file lives. Extracting them properly means reading the space manager's allocation bitmaps rather than trusting a tool's idea of "unallocated".

■ CAUTION — THIS DOES NOT WORK ON THE ENCRYPTED VOLUME

Free blocks belonging to a FileVault-encrypted volume contain ciphertext encrypted with per-file keys that are gone along with their inodes. There is nothing to recover: the plaintext is unrecoverable even with the volume password, because the per-file key was destroyed with the file's crypto state record.

Free-space work is therefore productive on the unencrypted volumes only — System, Preboot, Recovery, VM — and on any unencrypted external media images you hold. Know this before you spend a day on it. It is the single most common wasted effort on a FileVault case.

45.1 Reading the allocation bitmap

# the space manager object id comes from the container superblock at 0x98
python3 - <<'PY'
import struct
IMG='/evidence/mbp-001.dd'; START=524308480; BS=4096
f=open(IMG,'rb'); f.seek(START); b=f.read(BS)
print('spaceman oid :', struct.unpack_from('<Q', b, 0x98)[0])
print('omap oid     :', struct.unpack_from('<Q', b, 0xA0)[0])
print('block count  :', struct.unpack_from('<Q', b, 0x28)[0])
PY

The space manager points at chunk-info blocks, each of which points at a bitmap block covering a run of container blocks — one bit per block, set meaning allocated. Walking that structure gives you an authoritative free list. For unencrypted volumes, extract those blocks and treat the result as a carving target:

# once you have a list of free block addresses in freeblocks.txt
while read blk; do
     dd if=/evidence/mbp-001.dd bs=4096 skip=$(( (524308480/4096) + blk )) \
        count=1 status=none
   done < freeblocks.txt > ~/cases/001/05-carve/freespace.raw

bulk_extractor -o ~/cases/001/05-carve/freespace-be ~/cases/001/05-carve/freespace.raw
photorec /d ~/cases/001/05-carve/freespace-pr ~/cases/001/05-carve/freespace.raw
▸ TIP — TRIAGE BY ENTROPY BEFORE CARVING

Most free space is zeroes or ciphertext. Measure before you carve: split the extracted free space into chunks, compute entropy per chunk, and only carve the regions that look like structured data. §58 has the method. It routinely turns an overnight carve into a ten-minute one.

46Verifying the seal

The sealed System volume carries a SHA-256 for every file it contains, and a Merkle root over the whole set. This gives you two capabilities: proving the OS was not modified, and — more usefully — a complete, version-exact known-good hash set.

46.1 Read the stored seal and the broken flag

fsapfsinfo -o 524308480 -f 1 /evidence/mbp-001.dd | grep -i -A6 'integrity'
	Integrity metadata:
		Version           : 1
		Hash type         : SHA-256 (1)
		Root hash         : 4f9c2a...e71b
		Flags             : 0x00000000
# flags bit 0 = APFS_SEAL_BROKEN. Non-zero here is a finding on its own.

46.2 Verify files against their FILE_INFO hashes

# hash every file on the mounted System volume
find /mnt/sys/apfs1 -type f -print0 | \
    xargs -0 -P4 sha256sum > ~/cases/001/06-analysis/system-actual.sha256

# compare against the hashes APFS itself stores per file.
# fsapfsinfo exposes them per entry; mac_apt's plugin does this in bulk.
python3 ~/tools/mac_apt/mac_apt.py -o ~/cases/001/06-analysis/macapt \
    MOUNTED /mnt/sys/apfs1 UNIFIEDLOGS BASICINFO
▲ DEVIL — A MODIFIED SYSTEM BINARY IS NOT SUBTLE, AND THAT IS THE POINT

Modifying the sealed volume requires disabling SIP, booting to recovery, and reducing security — all of which leave records (unified log, Preboot LocalPolicy, NVRAM). An attacker who does it anyway is either very confident or very careless. Either way the mismatch between a file's actual SHA-256 and its stored FILE_INFO hash names the modified file precisely.

Remember your own footprint. You disabled SIP during acquisition (§1.2). That does not break the seal by itself — it changes the boot policy, not the volume — but confirm the timing of any Preboot changes against your acquisition record before attributing them to anyone else.

46.3 Using the seal as a hash set

The more valuable everyday use. Every file on the System volume has an authoritative hash placed there by Apple for this exact build. Extract them all and use the set to eliminate known-good files across your entire examination — more precise than NSRL, and already on your image.

▲ DEVIL — com.apple.macl NAMES THE APPLICATION THAT OPENED THE FILE

When a user opens a file through a sandboxed app's file dialog, macOS writes an entry into com.apple.macl recording the UUID of the application granted access. It is not a timestamp and not a log — it is a durable record that this specific application was given access to this specific file, and it survives copying the file to another location and another volume.

Practical uses: proving a document was opened by a particular application even though the app's own recent-items list was cleared; establishing that a file copied to a USB stick had previously been opened on this machine; and linking a file to an application that has since been deleted. Almost nothing in the standard toolchain surfaces it — you have to ask for it by name.

getfattr -n com.apple.macl -e hex --only-values \
    /mnt/data/apfs5/Users/jdoe/Documents/plans.pdf
▸ TIP — lastuseddate#PS IS A BETTER "OPENED" TIMESTAMP THAN atime

Access times on macOS are unreliable — updated inconsistently, and clobbered by backup and indexing processes touching every file. com.apple.lastuseddate#PS is written by Launch Services when a document is actually opened by a user, and it is a much stronger indicator of human interaction. It is a little-endian timespec: 8 bytes of Unix seconds, 8 bytes of nanoseconds.

getfattr -n 'com.apple.lastuseddate#PS' -e hex --only-values file.pdf | \
  sed 's/^0x//' | head -c16 | \
  python3 -c "import sys,struct,datetime;
d=bytes.fromhex(sys.stdin.read());
print(datetime.datetime.utcfromtimestamp(struct.unpack('<q',d)[0]))"

48decmpfs and compressed payloads

macOS transparently compresses files, storing the compressed data either inline in the com.apple.decmpfs extended attribute or in the resource fork. The file reports its uncompressed size and has no data extents at all.

TypeAlgorithmStorage
3 / 4zlib3 = inline in xattr, 4 = resource fork
7 / 8LZVN7 = inline, 8 = resource fork
11 / 12LZFSE11 = inline, 12 = resource fork
▲ DEVIL — A FILE WITH NO EXTENTS THAT IS NOT EMPTY

Two consequences that bite:

Tools disagree. apfs-fuse decompresses transparently and shows you the real content. TSK and some libfsapfs paths may report the file's logical size but return no data, making it look like an empty or sparse file. If icat gives you nothing for a file that apfs-fuse shows as 40 KB of text, it is compressed — not deleted, not corrupt.

It is a hiding place. Content stored in a resource fork or decmpfs attribute is invisible to anything that only walks data extents — including most carvers and any script that reads block allocations. Sweep for the attribute explicitly rather than assuming your tools handled it.

getfattr -R -n com.apple.decmpfs --only-values /mnt/data/apfs5/Users/ 2>/dev/null | head
# files carrying a resource fork are worth enumerating too
getfattr -R -m 'com.apple.ResourceFork' /mnt/data/apfs5/Users/ 2>/dev/null | \
    grep '^# file' | head -40

49Preboot and Recovery volume analysis

Two unencrypted volumes that most examinations skip entirely. They are small, they are rarely modified, and that combination makes any modification meaningful.

49.1 Preboot

fsapfsmount -o 524308480 -f 2 /evidence/mbp-001.dd /mnt/preboot
find /mnt/preboot/apfs2 -maxdepth 3 | head -40
/mnt/preboot/apfs2/<DataVolumeUUID>
/mnt/preboot/apfs2/<DataVolumeUUID>/System/Library/CoreServices
/mnt/preboot/apfs2/<DataVolumeUUID>/var/db
/mnt/preboot/apfs2/<DataVolumeUUID>/LocalPolicy
/mnt/preboot/apfs2/Cryptexes
▲ DEVIL — LocalPolicy RECORDS THE SECURITY DOWNGRADE

On Apple Silicon, LocalPolicy/*.img4 encodes the machine's boot security posture: Full, Reduced or Permissive security; whether SIP is disabled; whether third-party kexts are allowed; whether the boot policy permits an unsealed system volume.

A machine in Reduced or Permissive security was deliberately downgraded by someone with physical access and the admin password. If your case involves a modified system volume, disabled SIP, or unsigned kernel extensions, this is the corroborating artifact — and it is on an unencrypted volume you can read without any password.

Your own acquisition modified this. You ran csrutil disable (§1.2), which rewrites LocalPolicy. Compare timestamps against your acquisition record before attributing the downgrade to the subject. If the downgrade predates your acquisition, it was not you.

find /mnt/preboot/apfs2 -name '*.img4' -printf '%TY-%Tm-%Td %T@ %p\n' | sort -k2 -n

Also on Preboot: per-volume boot support files, and var/db/ containing volume ownership records — which identify the accounts permitted to unlock and boot the machine. An unexpected entry there is an account with FileVault unlock rights.

49.2 Recovery

recoveryOS changes only when macOS is updated. Enumerate it, note the timestamps, and treat any file whose modification time does not correspond to an OS update in install.log as requiring an explanation. Persistence installed here survives an erase-and-reinstall of the main system, which is exactly why sophisticated actors like it.

fsapfsmount -o 524308480 -f 3 /evidence/mbp-001.dd /mnt/recovery
find /mnt/recovery/apfs3 -type f -printf '%TY-%Tm-%Td %p\n' | sort | tail -30
# cross-check the dates against OS update events

50The VM volume

Swap and hibernation. Historically a goldmine of process memory; on modern hardware, much less so — but worth ten minutes.

fsapfsmount -o 524308480 -f 4 /evidence/mbp-001.dd /mnt/vm
ls -la /mnt/vm/apfs4/
-rw------- 1 root root 1073741824 Jul 30 02:11 swapfile0
-rw------- 1 root root 1073741824 Jul 30 02:38 swapfile1
-rw------- 1 root root 8589934592 Jul 29 23:04 sleepimage
■ CAUTION — SET YOUR EXPECTATIONS CORRECTLY

macOS encrypts swap by default, and on Apple Silicon the sleepimage is encrypted with a key held in the Secure Enclave that is discarded at wake. You will usually find high-entropy noise and nothing else. Do not spend a day on it, and do not report "swap was encrypted" as though it were an adverse finding — it is the default configuration.

What is still worth extracting:

  • Timestamps and sizes. Swapfile count and modification times indicate memory pressure and roughly when the machine was under load. The sleepimage's timestamp is the last time the machine hibernated — a reliable "machine was here, doing this, at this time" data point.
  • Entropy check, cheaply. If entropy is not uniformly high, something is unencrypted and worth looking at.
ent /mnt/vm/apfs4/swapfile0 | head -3
Entropy = 7.999812 bits per byte.
# ~8.0 means encrypted or compressed — nothing to extract
