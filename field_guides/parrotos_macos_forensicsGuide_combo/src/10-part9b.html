51Firmlink confusion and path hiding

§12.3 covered firmlinks as a translation problem. They are also a hiding technique, because the unified view macOS presents is a subset of what is physically on the two volumes.

51.1 Shadowed directories

When /Library is firmlinked to the Data volume's Library, the System volume's own Library at that path is shadowed — physically present, never shown. The same applies to /Users, /opt, /usr/local and every other firmlink target.

▲ DEVIL — CONTENT VISIBLE ONLY WHEN THE VOLUMES ARE SEPARATED

Files placed in a shadowed location are invisible to every live-system triage tool, to find /, to Spotlight, and to any script that walks the running filesystem. They are plainly visible to you, because you mounted the two volumes separately.

This is an advantage of dead-box analysis that live response cannot match. Enumerate both volumes independently and compare against the firmlink table — anything in a shadowed path is, by definition, something the running system was never showing anyone.

# what exists on the System volume at firmlinked paths — normally near-empty
for p in Library Users Applications opt cores; do
     echo "== /$p on SYSTEM volume"; ls -la /mnt/sys/apfs1/$p 2>/dev/null | head
   done

Note that the System volume is sealed, so writing there breaks the seal (§46) — which makes this a loud technique, not a quiet one. The quiet version is the Data volume's own shadowed paths, which are not sealed at all.

51.2 Ordinary hiding, which is more common

# BSD hidden flag — invisible in Finder, visible to you
find /mnt/data/apfs5/Users -flags +hidden 2>/dev/null | head
# (Linux find lacks -flags; read bsd_flags via fsapfsinfo or check UF_HIDDEN=0x8000)

# names designed to be overlooked
find /mnt/data/apfs5/Users -name '.*' -type f | grep -vE '\.(DS_Store|localized|CFUserText)' | head -40
find /mnt/data/apfs5 -name '* ' -o -name ' *' 2>/dev/null | head   # trailing/leading spaces

# non-ASCII and homoglyph filenames
find /mnt/data/apfs5/Users -print0 | perl -0ne 'print if /[^\x00-\x7F]/' | head -30

# deeply nested or oddly-timestamped directories under /private/var/folders
find /mnt/data/apfs5/private/var/folders -type f -newermt '2026-07-25' \
     -not -path '*Cache*' 2>/dev/null | head -40

52Slack, sibling links and oversized xattrs

52.1 Hard links as an anti-deletion technique

APFS records hard links through sibling-link and sibling-map records: one inode, several names. Deleting one name decrements the link count; the data survives while any name remains.

# files with more than one link — rare on a normal Mac outside a few system areas
find /mnt/data/apfs5 -type f -links +1 -printf '%n %i %p\n' 2>/dev/null | \
    sort -rn | head -40
▲ DEVIL — "DELETED" DATA WITH A SECOND NAME

A second hard link in an obscure location means that deleting the obvious copy destroys nothing. Conversely, if you find an inode with a link count higher than the number of names you can locate, there is a name you have not found — possibly in a shadowed path (§51), possibly in a snapshot. Both are worth chasing.

52.2 Oversized extended attributes

Small xattrs live inline in the catalog record. Once an attribute exceeds roughly 3.8 KB, APFS promotes it to its own data stream — meaning an extended attribute can hold arbitrarily large content that does not appear in the file's size, does not appear in directory listings, and is skipped by almost every carver and copying tool.

# rank every xattr on a tree by value size — outliers first
getfattr -R -d -m '.*' -e base64 /mnt/data/apfs5/Users/ 2>/dev/null | \
  awk -F= '/=0s/ {print length($2), $1}' | sort -rn | head -20
41208 com.apple.ResourceFork
39114 com.apple.decmpfs
 8822 com.apple.macl

Anything unexpectedly large, or any attribute with a name you do not recognise, deserves extraction and a file check. This is a genuinely obscure hiding place and it survives copying the file with tools that preserve xattrs.

52.3 Slack space, honestly

APFS allocates in block units, so a file's final block has unused tail bytes. On a spinning disk that tail would hold residue from a previous file. On an SSD with TRIM — which is every machine you will examine — freed blocks are discarded by the controller and typically read back as zeroes, and APFS itself zero-fills in many paths. Treat slack recovery on modern Mac hardware as a long shot, not a technique. Check it if it is cheap; do not build a theory on it.

The same logic as inode numbers, applied to databases. In History.db, chat.db, knowledgeC.db and the rest, rowid increases with insertion order. A row bearing an old timestamp but a high rowid was inserted recently and backdated. One query finds them:

53.2 The nanosecond tell

▲ DEVIL — ZEROED NANOSECONDS

Timestamps written by the kernel during normal filesystem activity carry a full nanosecond component — effectively random. Timestamps set deliberately through most tooling (touch -t, SetFile -d, and the majority of timestomping utilities) specify whole seconds, leaving the nanosecond field exactly zero.

Across a normal volume, files with all-zero nanoseconds on all four timestamps are a small minority. A cluster of them, in one directory, on files relevant to your case, is a strong signal.

awk -F'|' '$9%1==0 && $10%1==0 {print $2}' body.txt | head
# better: read nanoseconds directly, where the body file truncates them
stat --printf='%y|%z|%w|%n\n' /mnt/data/apfs5/Users/jdoe/Library/LaunchAgents/*.plist
2019-03-14 09:12:00.000000000 +0000|...      ← all zeroes: set, not written

53.3 Working a contradiction

The method, in order:

  1. Fix the claim. "This file was created 2019-03-14."
  2. Ask each witness independently. Inode ordering, change_time, FSEvents, snapshots, ExecPolicy, unified log, parent directory.
  3. Count agreements. One dissenting witness is usually a parser or timezone error. Three or more dissenting, all pointing at the same alternative time, is a finding.
  4. Explain the mechanism. "The inode number places creation between two files created at 02:38 on 2026-07-30; the change time is 02:39 the same day; the file is absent from the 02:15 snapshot and present in the 03:15 one." That is a defensible statement. "The timestamp looked wrong" is not.

▲ DEVIL — THE CLEANUP IS LOUDER THAN THE INTRUSION

Deleting evidence is itself an event, and it happens after the activity it conceals — which means it is the most recent thing on the machine and sits at the top of every timeline. When you cannot find the intrusion, stop looking for it and look for the cleanup instead. Then work backwards from its timestamp.

▲ DEVIL — THE PASSWORD HASH IS IN THE ACCOUNT PLIST

ShadowHashData inside the user plist holds the SALTED-SHA512-PBKDF2 verifier — salt, iteration count and hash. Practically, for your case the more useful angle is that a deleted account's plist survives in snapshots, complete with its GeneratedUID. 58Entropy mapping the container

A cheap way to find the interesting regions of a very large image: measure randomness and look at what does not fit its surroundings.

cat > ~/cases/001/06-analysis/entropy_map.py <<'PY'
#!/usr/bin/env python3
import sys, math, collections
PATH  = sys.argv[1]
CHUNK = int(sys.argv[2]) if len(sys.argv) > 2 else 1 << 20   # 1 MiB

def entropy(b):
    if not b: return 0.0
    c = collections.Counter(b); n = len(b)
    return -sum((v/n) * math.log2(v/n) for v in c.values())

with open(PATH, 'rb') as f:
    off = 0
    while True:
        d = f.read(CHUNK)
        if not d: break
        e = entropy(d)
        bar = '#' * int(e * 6)
        print(f'{off:014d}  {e:5.3f}  {bar}')
        off += len(d)
PY

python3 ~/cases/001/06-analysis/entropy_map.py /evidence/mbp-001.dd > entropy.txt

# regions that are neither empty nor encrypted — structured data worth carving
awk '$2 > 3.0 && $2 < 7.0 {print}' entropy.txt | head -40
EntropyUsually means
0.0 – 1.0Zeroes or a single repeated byte — unused or wiped
3.0 – 6.0Text, XML, source, SQLite, plists — carve here
6.0 – 7.5Executables, images, mixed structured content
7.9 – 8.0Encrypted or compressed. Uniform across the encrypted volume; interesting only when it appears somewhere it should not
▸ TIP — LOOK FOR THE INVERSION

The productive question is not "where is the high entropy" — on a FileVault machine that is everywhere. It is: where is the low entropy inside a region that should be uniformly high? A run of plaintext inside the encrypted volume's block range means something was written outside the encryption path. Equally, a high-entropy blob sitting inside an otherwise ordinary user directory is a packed binary, an archive, or an encrypted container worth identifying.

59Honest limits

A short chapter, and the most important one for your report. These are the questions this image cannot answer, and saying so plainly is what makes the rest of your findings credible.

MemoryGone. Running processes, injected code, decrypted keys, network connections and anything that never touched disk are unrecoverable. Volatility has no use here. NVRAM and firmwareNot in the image. Boot arguments, EFI variables and firmware-level implants are outside a disk acquisition entirely. Secure Enclave stateKey material, biometric templates and the hardware key hierarchy never leave the SEP. Encrypted free spaceDeleted content on the FileVault volume is unrecoverable — the per-file key died with the file (§45). Overwritten dataCopy-on-write delays reuse but does not prevent it. Anything reallocated is gone. Server-side dataiCloud, iMessage history not synced locally, and any cloud service state exist elsewhere and require separate legal process. Network activitymacOS keeps no persistent connection log. Beyond a few unified-log entries and browser history, outbound traffic left no trace on this disk. Who was at the keyboardNothing on the disk identifies a human. Account attribution is attribution to an account, and should always be worded that way.
■ CAUTION — STATE THE LIMITS BEFORE YOU ARE ASKED

Every limitation above will be raised by someone reviewing your work. Raising them yourself, in the methodology section, costs nothing and removes the entire line of attack. An examiner who volunteers what their evidence cannot show is far more persuasive than one who has it extracted from them.
