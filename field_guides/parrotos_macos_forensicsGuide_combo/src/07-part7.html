24The unified log

Since Sierra, almost everything the system says about itself goes into the unified log: process launches, network state, authentication, mounts, USB attachment, sandbox violations, TCC decisions. It is the richest single artifact on the machine and the most annoying to read off-Mac.

Log data/private/var/db/diagnostics/ → <DATA>/private/var/db/diagnostics/ String tables/private/var/db/uuidtext/ → <DATA>/private/var/db/uuidtext/ 
diagnostics/
├── Persist/        0000000000000001.tracev3   long-lived records — your main source
├── Special/        short-lived, higher-volume records
├── Signpost/       performance instrumentation
├── HighVolume/     very chatty subsystems
├── logdata.LiveData.tracev3    the in-flight buffer at shutdown/acquisition
└── Persist/...
uuidtext/
├── XX/YYYYYYYY...  per-binary format-string tables
└── dsc/            shared cache string tables
▲ DEVIL — THE LOG IS USELESS WITHOUT uuidtext

.tracev3 files do not contain log messages. They contain format string references and arguments; the actual text lives in uuidtext/, keyed by the UUID of the binary that emitted it. Copy only diagnostics/ and you get a parse full of <missing format string>. Always extract both directories together, preserving their relative layout. This single mistake accounts for most "the unified log parser doesn't work" complaints.

# extract both trees, preserving structure and timestamps

# Mandiant's Rust parser — fastest and most complete

▲ DEVIL — GAPS ARE THE FINDING

Unified log files rotate and are pruned automatically, so absence alone proves nothing. But .tracev3 files carry sequential identifiers, and the record stream is continuous. A missing file in the sequence, or a clean multi-hour hole in an otherwise chatty log with no corresponding shutdown record, is not normal pruning. §54 covers how to distinguish rotation from deletion.

25FSEvents

Every APFS volume keeps a low-level record of filesystem changes in /.fseventsd/ at its root. It is coarse — it records that a path changed and roughly how, not who or exactly when — but it reaches back weeks or months and it records paths that no longer exist.

Location<DATA>/.fseventsd/ and on every other volume too Formatgzip-compressed binary streams, named with hex event IDs; plus fseventsd-uuid 
ls /mnt/data/apfs5/.fseventsd/ | head
0000000000a1b2c3
0000000000a1b2d4
fseventsd-uuid

cp -a /mnt/data/apfs5/.fseventsd ~/cases/001/03-extract/logs/

python3 ~/tools/FSEventsParser/FSEParser_V4.1.py \
    -c case001 -s ~/cases/001/03-extract/logs/.fseventsd \
    -o ~/cases/001/04-timeline/fsevents/

# the output is per-path with change-type flags
grep -i 'Downloads' ~/cases/001/04-timeline/fsevents/*.tsv | head
▲ DEVIL — FSEVENTS REMEMBERS DELETED FILES BY NAME

An FSEvents record persists long after the file it describes is gone. You will routinely find entries for files that exist nowhere on the volume, in no snapshot, and in no carved output — proving that a file with that exact path existed and was created, modified, renamed or removed. For establishing that a tool was present on the machine before being wiped, this is often the only surviving evidence. It carries no content, but "a file named Users/jdoe/Library/LaunchAgents/com.apple.softwareupdated.plist was created and later removed" is frequently the whole point.

Check /.fseventsd on every volume, not just Data. And note that the presence of a fseventsd-uuid that differs from the one in your snapshots means the volume's event history was reset — which happens on erase, and on deliberate deletion of the directory.

26Spotlight metadata stores

Spotlight indexes far more than filenames — it stores per-file metadata attributes, including where a file was downloaded from, its content type, its title, and in many cases a text preview. Crucially, index entries can survive the file itself.

Volume store<DATA>/.Spotlight-V100/Store-V2/<UUID>/store.db and .store.db Also present onevery mounted volume, including external drives that were attached User store<DATA>/private/var/folders/<xx>/<yyy>/0/com.apple.Spotlight/ 
find /mnt/data/apfs5/.Spotlight-V100 -name 'store.db' -o -name '.store.db'

python3 ~/tools/spotlight_parser/spotlight_parser.py \
    /mnt/data/apfs5/.Spotlight-V100/Store-V2/3E9A.../store.db \
    ~/cases/001/06-analysis/spotlight/

# the attribute that matters most: download provenance, retained per file
grep -i 'kMDItemWhereFroms\|kMDItemDownloadedDate' \
    ~/cases/001/06-analysis/spotlight/*.txt | head -40
▸ TIP — EXTERNAL DRIVE STORES ARE A HISTORY OF OTHER MACHINES

If any external volume was indexed on this Mac, its .Spotlight-V100 travelled with it. Conversely, if the subject attached a drive that had been indexed elsewhere, its store may describe files from a completely different computer. Always check which volume UUID a store belongs to before attributing its contents to this machine.

27Quarantine and download provenance

Three independent records of where a file came from. They disagree often enough that you should collect all three.

27.1 The quarantine database

# ~/Library/Preferences/com.apple.LaunchServices.QuarantineEventsV2
Q=/mnt/data/apfs5/Users/jdoe/Library/Preferences/com.apple.LaunchServices.QuarantineEventsV2
cp -a "$Q"* ~/cases/001/03-extract/db/

sqlite3 ~/cases/001/03-extract/db/com.apple.LaunchServices.QuarantineEventsV2 \
  "SELECT datetime(LSQuarantineTimeStamp + 978307200, 'unixepoch') AS ts,
          LSQuarantineAgentName, LSQuarantineDataURLString, LSQuarantineOriginURLString
   FROM LSQuarantineEvent ORDER BY ts DESC LIMIT 40;"
2026-07-21 19:03:58|Safari|https://cdn.example.net/installer.pkg|https://example.net/download
● NOTE — THE 978307200 CONSTANT

Apple timestamps in these databases are Mac absolute time: seconds since 2001-01-01 UTC. Add 978307200 to convert to Unix epoch. You will type this number constantly — see Appendix C. Getting it wrong shifts every timestamp by 31 years, which is at least obvious. Forgetting that some tables use Unix epoch and others use Mac absolute in the same database is the subtler trap.

27.2 The quarantine extended attribute

# the xattr rides on the file itself and survives copying within the volume
getfattr -n com.apple.quarantine -d /mnt/data/apfs5/Users/jdoe/Downloads/installer.pkg
com.apple.quarantine="0083;68d3f1a6;Safari;F1E2D3C4-..."
#  flags ; hex mac-absolute timestamp ; agent ; event UUID (joins to the DB above)

# sweep the whole user tree for quarantined files, including ones the DB forgot
getfattr -R -n com.apple.quarantine /mnt/data/apfs5/Users/ 2>/dev/null | \
    grep -B1 'com.apple.quarantine' | head -60

27.3 The where-from attribute

# com.apple.metadata:kMDItemWhereFroms is a binary plist inside an xattr
getfattr -n com.apple.metadata:kMDItemWhereFroms --only-values \
    /mnt/data/apfs5/Users/jdoe/Downloads/installer.pkg > /tmp/wf.bplist
plistutil -i /tmp/wf.bplist -o -
<array>
  <string>https://cdn.example.net/installer.pkg</string>
  <string>https://example.net/download</string>
</array>
▲ DEVIL — ABSENCE OF QUARANTINE IS ITSELF A SIGNAL

Anything downloaded by a normal browser gets quarantined. A recently-created executable or application bundle in a user directory with no quarantine xattr arrived by a route that does not set it: curl, wget, scp, AirDrop in some configurations, a package installer running as root, extraction from an archive by a non-quarantine-aware tool, or deliberate removal with xattr -d. On a machine whose user only ever installs things from the browser, an unquarantined binary in ~/Downloads is worth more attention than a quarantined one.

▲ DEVIL — POWERLOG OUTLIVES THE APPLICATION

Powerlog records per-process energy and activity for weeks, and it keeps recording bundle identifiers for applications that have since been deleted. An application installed, run once and removed leaves no bundle, no Launch Services entry, and often no log — but it leaves a powerlog row. Combined with knowledgeC's focus intervals you can reconstruct that an unknown binary ran, for how long, and when, from an artifact almost nobody wipes.

sqlite3 CurrentPowerlog.PLSQL ".tables" | tr ' ' '\n' | grep -i 'app\|process' | head
▸ TIP — USE APOLLO RATHER THAN HAND-WRITTEN SQL

APOLLO ships hundreds of vetted queries across these databases and normalises the output into one timeline. Writing your own SQL is for when you need something APOLLO does not have. §61.

29TCC — the permission ledger

Transparency, Consent and Control records every privacy permission ever granted or denied: camera, microphone, screen recording, full disk access, accessibility, automation. For an intrusion case it is close to a list of what the attacker wanted.

System<DATA>/Library/Application Support/com.apple.TCC/TCC.db Per user<DATA>/Users/<u>/Library/Application Support/com.apple.TCC/TCC.db 
sqlite3 TCC.db "
SELECT service, client, client_type, auth_value, auth_reason,
       datetime(last_modified,'unixepoch') AS modified
FROM access ORDER BY last_modified DESC;"
kTCCServiceScreenCapture|com.example.updater|0|2|3|2026-07-30 02:39:44
kTCCServiceAccessibility|com.example.updater|0|2|3|2026-07-30 02:39:51
ServiceWhy an attacker wants it
kTCCServiceAccessibilitySynthetic input and full UI control — the single most abused permission on macOS
kTCCServiceScreenCaptureScreen recording
kTCCServiceSystemPolicyAllFilesFull Disk Access — reads every user file including other apps' databases

▲ DEVIL — TCC IS A TIMELINE OF INTENT

last_modified tells you when each grant happened, and grants cluster: a user installing a legitimate screen-sharing tool produces two or three related entries within a minute. An unfamiliar bundle identifier acquiring Accessibility and Screen Recording and Full Disk Access inside the same thirty seconds is a compromise timestamp accurate to the second.

Cross-reference every client value against the bundles actually present on disk. A TCC entry naming a bundle that no longer exists means the application was removed after being granted access — and the entry survived the cleanup.

30Notifications, installs and audit logs

30.1 Notification Center

Holds delivered notification content — message previews, mail subjects, alerts — often including text from applications whose own databases were cleared.

find /mnt/data/apfs5/private/var/folders -path '*com.apple.notificationcenter/db2/db' 2>/dev/null
sqlite3 db "SELECT datetime(delivered_date+978307200,'unixepoch'), app_id, data
             FROM record ORDER BY delivered_date DESC LIMIT 30;"
# the 'data' column is an NSKeyedArchiver blob — see §33

30.2 install.log

Plain text, long-retained, and it records every package installation, OS update and — importantly — every installer invocation regardless of source.

grep -iE 'installer|package|Install(ed|ing)' \
    /mnt/data/apfs5/private/var/log/install.log | tail -100

# rotated copies go back much further than people expect
ls -la /mnt/data/apfs5/private/var/log/install.log*
zgrep -i 'pkg' /mnt/data/apfs5/private/var/log/install.log.*.gz | tail -50

30.3 OpenBSM audit logs

The BSM audit trail is the closest thing macOS has to Linux auditd. It is off by default on recent macOS, but where it was enabled — managed fleets, hardened builds — it is authoritative process-execution evidence.

ls /mnt/data/apfs5/private/var/audit/ | tail
20260730024155.20260730031200
20260730031200.not_terminated

# Debian has no praudit. Parse with mac_apt's plugin, or with Python:
python3 ~/tools/mac_apt/mac_apt.py -o ~/cases/001/06-analysis/macapt \
    MOUNTED /mnt/data/apfs5 BASICINFO
● NOTE — CHECK WHETHER AUDITING WAS EVEN ON

Read <DATA>/private/etc/security/audit_control before drawing conclusions from an empty /var/audit. If auditing was disabled the absence means nothing. If it was enabled and the directory is empty or truncated, that is a different and much more interesting fact.

32SQLite deep dive

Nearly every artifact above is SQLite. Treating those files as "run a SELECT and move on" throws away most of the available evidence.

32.1 Always take the whole set

# NEVER copy just the .db
cp -a chat.db chat.db-wal chat.db-shm ~/cases/001/03-extract/db/
▲ DEVIL — THE NEWEST DATA IS IN THE -wal, NOT THE DATABASE

In WAL mode — which macOS uses almost everywhere — committed transactions live in the -wal file until a checkpoint folds them into the main database. On a machine that was imaged without a clean shutdown, the most recent hours of activity exist only in the -wal. Copy the .db alone and you silently lose the very period you most care about.

Worse: opening the database with sqlite3 while the -wal is present causes an automatic checkpoint, modifying your copy. Work on copies, and hash before and after.

32.2 Reading the WAL separately

# see what the WAL holds before it is merged
python3 ~/tools/walitean/walitean.py -f chat.db-wal -o ~/cases/001/06-analysis/wal/

# or force a read-only open that will not checkpoint
sqlite3 "file:chat.db?immutable=1" "PRAGMA journal_mode; SELECT count(*) FROM message;"

32.3 Deleted rows

# sqlite's own recovery — rebuilds from pages, including some freed content
sqlite3 chat.db ".recover" > recovered.sql
sqlite3 recovered.db < recovered.sql

# undark walks freelist and unallocated page space for deleted records
undark -i chat.db --freespace > deleted-rows.txt

# crude but effective: strings across the raw database file
strings -a -t d chat.db | grep -i 'suspicious-term'
▸ TIP — CHECK auto_vacuum BEFORE YOU INVEST TIME

PRAGMA auto_vacuum; returning 1 (FULL) means freed pages are returned to the OS immediately and deleted-row recovery will yield little. Returning 0 (NONE) means freed pages linger and recovery is worth the effort. One query saves an afternoon.

33Plists and NSKeyedArchiver without plutil

Property lists come in three flavours: XML, binary (bplist), and binary containing an NSKeyedArchiver object graph. The third looks like nonsense until deserialised, and a great deal of modern macOS state is stored that way.

33.1 XML and binary plists

# Debian's libplist-utils replaces plutil for straightforward cases
plistutil -i com.apple.dock.plist -o - | head -40

# Python handles both formats natively and is easier to script
python3 -c "
import plistlib,sys,json
d=plistlib.load(open(sys.argv[1],'rb'))
print(json.dumps(d,indent=2,default=str))" com.apple.dock.plist

33.2 NSKeyedArchiver

Recognise it by a top-level $archiver, $objects, $top structure. plistlib will parse it and hand you an unusable flat object table; you need a deserialiser to rebuild the graph.

pip install nska-deserialize
python3 - <<'PY'
import nska_deserialize as nd, sys, json
with open('/path/to/com.apple.LSSharedFileList.RecentDocuments.sfl2','rb') as f:
    obj = nd.deserialize_plist(f)
print(json.dumps(obj, indent=2, default=str))

■ CAUTION — PLIST TIMESTAMPS ARE MAC ABSOLUTE

plistlib returns real datetime objects for XML plist dates and handles them correctly. But a raw numeric timestamp stored inside a plist value — which is how most Apple code stores time — is almost always Mac absolute (2001 epoch) and needs +978307200. If a date comes out in 1988, you forgot. If it comes out in 2058, you added it twice.
