The Persistence Map

Everywhere on Ventura and later that code can arrange to run again. Ordered roughly by how often it is actually used, not by how exotic it is — because the boring locations are where the findings usually are, and the obscure ones are where a competent adversary goes when they expect you to look at the boring ones.

34launchd — agents and daemons

Still the overwhelming majority of real-world macOS persistence. Six directories, and you must check all six because they differ in privilege and in which volume they live on.

Path on your mountRuns asNotes
<DATA>/Library/LaunchDaemons/root, at bootHighest value. Writable, survives logout, full privilege
<DATA>/Library/LaunchAgents/each user, at loginWritable, applies to every user on the machine
<DATA>/Users/<u>/Library/LaunchAgents/that userNo admin rights needed to create. Most common foothold
<SYS>/System/Library/LaunchDaemons/rootSealed — a modification here breaks the seal (§46)
<SYS>/System/Library/LaunchAgents/each userSealed, same reasoning
<DATA>/Library/StartupItems/rootLong deprecated; its presence at all is anomalous

34.1 Sweep and triage

# collect every job definition with its path, sorted by modification time
find /mnt/data/apfs5/Library/Launch{Daemons,Agents} \
     /mnt/data/apfs5/Users/*/Library/LaunchAgents \
     /mnt/sys/apfs1/System/Library/Launch{Daemons,Agents} \
     -name '*.plist' -printf '%T@ %p\n' 2>/dev/null | sort -rn | head -40

# dump the interesting keys from each
for p in /mnt/data/apfs5/Library/LaunchDaemons/*.plist; do
    echo "=== $p"
    plistutil -i "$p" -o - | grep -A3 -E 'Label|Program|RunAtLoad|KeepAlive|StartInterval|WatchPaths|DYLD'
  done

34.2 What makes a job suspicious

KeyRead it as
LabelApple-lookalike names are the classic tell: com.apple.softwareupdated in ~/Library/LaunchAgents is not Apple's — Apple's live on the sealed volume
Program / ProgramArgumentsThe payload. Interpreters (osascript, python3, bash -c, curl | sh) and paths in /tmp, /usr/local, ~/Library are all elevated interest
RunAtLoad + KeepAliveStart immediately and restart forever — the persistence idiom
StartInterval / StartCalendarIntervalBeaconing. A short interval on a non-Apple job is a C2 heartbeat until shown otherwise
WatchPaths / QueueDirectoriesTrigger on filesystem activity — used to re-establish persistence when a file is deleted
StartOnMountFires whenever any volume mounts — used to target removable media
EnvironmentVariablesDYLD_INSERT_LIBRARIES here is library injection into whatever the job runs
LimitLoadToSessionTypeAqua = GUI login only; Background/LoginWindow = runs pre-login
▲ DEVIL — THE PLIST WITHOUT A BINARY, AND THE BINARY WITHOUT A PLIST

Two asymmetric checks that catch cleanup attempts:

Orphaned plists. A job definition whose Program no longer exists on disk means the payload was removed but the persistence was not. The plist names the file, giving you a path to hunt in snapshots, FSEvents and Spotlight.

Orphaned disable records. <DATA>/private/var/db/com.apple.xpc.launchd/ holds disabled.plist and disabled-<uid>.plist, recording jobs explicitly enabled or disabled by label. Labels here that correspond to no plist on disk are the ghost of a job that once existed. Attackers routinely delete the plist and forget this file.

plistutil -i /mnt/data/apfs5/private/var/db/com.apple.xpc.launchd/disabled.plist -o -
# older layout, worth checking on upgraded systems:
# private/var/db/launchd.db/com.apple.launchd/overrides.plist

35BTM — the modern login-item store 13+

Ventura replaced the old login-items mechanism with Background Task Management. Every login item, launch agent, launch daemon and app-registered background task is recorded in a single database — and it retains entries for items that have since been removed.

Ventura+<DATA>/private/var/db/com.apple.backgroundtaskmanagement/BackgroundItems-v<N>.btm Pre-Ventura<DATA>/Users/<u>/Library/Application Support/com.apple.backgroundtaskmanagementagent/backgrounditems.btm FormatNSKeyedArchiver binary plist — see §33 
ls /mnt/data/apfs5/private/var/db/com.apple.backgroundtaskmanagement/
BackgroundItems-v9.btm  BackgroundItems-v8.btm

python3 - <<'PY'
import nska_deserialize as nd, json, glob
for p in glob.glob('/mnt/data/apfs5/private/var/db/com.apple.backgroundtaskmanagement/*.btm'):
    with open(p,'rb') as f:
        obj = nd.deserialize_plist(f)
    print('===', p)
    print(json.dumps(obj, indent=2, default=str)[:4000])
PY
▲ DEVIL — BTM KEEPS THE DEAD

The BTM store records items with a developer team identifier, a bundle path, an item type, and a disposition (enabled, disabled, allowed, removed by user). Entries persist after the item is deleted from disk. On a machine that was cleaned up, BTM frequently still names the launch agent, its executable path and its signing team — everything you need to identify what was there.

Note also the versioned filenames. Older BackgroundItems-v<N-1>.btm files often survive alongside the current one, giving you a historical view of persistence that predates the attacker's cleanup by weeks.

37Profiles, MDM and system extensions

37.1 Configuration profiles

A profile can install certificates, force proxy settings, add login items, and grant TCC permissions without prompting. On an unmanaged personal machine, any profile deserves scrutiny.

ls -la /mnt/data/apfs5/private/var/db/ConfigurationProfiles/Settings/
ls -la /mnt/data/apfs5/private/var/db/ConfigurationProfiles/Store/
ls -la "/mnt/data/apfs5/Library/Managed Preferences/"

# a profile installing a root CA is a full TLS interception capability
grep -rl 'com.apple.security.root\|PayloadType.*certificate' \
    /mnt/data/apfs5/private/var/db/ConfigurationProfiles/ 2>/dev/null

37.2 System extensions and kext approval

# installed system extensions and their state
plistutil -i /mnt/data/apfs5/Library/SystemExtensions/db.plist -o - | head -80
ls /mnt/data/apfs5/Library/SystemExtensions/

# user-approved kernel extensions, with team identifiers — SQLite
sqlite3 /mnt/data/apfs5/private/var/db/SystemPolicyConfiguration/KextPolicy \
  "SELECT team_id, bundle_id, allowed, flags FROM kext_policy;"
EQHXZ8M8AV|com.example.driver|1|8
▲ DEVIL — ExecPolicy IS A FIRST-EXECUTION LOG

Next to KextPolicy sits ExecPolicy, and it is one of the most under-used artifacts on macOS. Gatekeeper records executables the first time they run, with paths, signing information and timestamps — including for binaries that were later deleted.

sqlite3 /mnt/data/apfs5/private/var/db/SystemPolicyConfiguration/ExecPolicy ".tables"
legacy_exec_history_v4  policy_scan_cache  scan_detail  ...

sqlite3 /mnt/data/apfs5/private/var/db/SystemPolicyConfiguration/ExecPolicy "
SELECT datetime(timestamp,'unixepoch') AS first_seen, responsible_path, file_identifier
FROM policy_scan_cache ORDER BY timestamp DESC LIMIT 40;"

Read that as: a list of programs that ran on this machine for the first time, with dates. Cross-reference every path against what still exists on disk — the entries with no surviving file are your leads.

38Plugin and injection surfaces

macOS loads third-party code into system processes through a long list of plugin directories. Each is a persistence mechanism that involves no launchd job at all, which is precisely why they get used.

Location (system and ~/Library variants)Loaded into / triggered by
/Library/Security/SecurityAgentPlugins/Authorisation plugins — run at the login window, as root. Very high value
/Library/Audio/Plug-Ins/HAL/coreaudiod — the classic microphone-capture persistence
/Library/QuickLook/Thumbnail generation — triggered merely by viewing a folder
/Library/Spotlight/Metadata importers — triggered by indexing
/Library/Input Methods/Runs in every application that accepts text
/Library/ColorPickers/, /Library/PreferencePanes/Loaded on demand by UI
/Library/Screen Savers/Runs on idle
/Library/Internet Plug-Ins/Legacy, still loaded by some applications
~/Library/Services/, ~/Library/Workflows/Automator services and Folder Actions
App bundle Contents/XPCServices/, Contents/PlugIns/Code inside a legitimate app's bundle — inherits its TCC grants
 
# sweep every plugin surface at once, newest first
for d in "Security/SecurityAgentPlugins" "Audio/Plug-Ins/HAL" "QuickLook" "Spotlight" \
         "Input Methods" "ColorPickers" "PreferencePanes" "Screen Savers" "Internet Plug-Ins"; do
    for base in /mnt/data/apfs5/Library /mnt/data/apfs5/Users/*/Library; do
      [ -d "$base/$d" ] && find "$base/$d" -maxdepth 1 -mindepth 1 -printf '%TY-%Tm-%Td %p\n'
    done
  done | sort -r
▲ DEVIL — LOGIN AND LOGOUT HOOKS STILL WORK

Deprecated for over a decade, never removed. A single preference key runs an arbitrary script as root at every login or logout, with no plist in any LaunchAgents directory and no BTM entry.

plistutil -i /mnt/data/apfs5/Library/Preferences/com.apple.loginwindow.plist -o - | \
    grep -A2 -i 'LoginHook\|LogoutHook'

In the same file, check autoLoginUser (automatic login without a password) and, in ~/Library/Preferences/ByHost/com.apple.loginwindow.<UUID>.plist, TALAppsToRelaunchAtLogin — the "reopen windows when logging back in" list, which is another way to get an application launched at login with no persistence artifact.

39Unix-side persistence

macOS is BSD underneath and every traditional Unix mechanism still functions. These are often skipped by macOS-focused triage tools.

PathCheck for
Users/<u>/.zshrc, .zshenv, .zprofile, .bash_profileAppended commands, aliases shadowing real binaries, curl|sh
private/etc/zshenv, zprofile, profileSystem-wide shell startup — applies to every user
private/etc/sudoers, sudoers.d/NOPASSWD entries, unexpected users
Users/<u>/.ssh/authorized_keysAttacker public keys — check from= and command restrictions too
private/etc/ssh/sshd_config, sshd_config.d/PermitRootLogin, alternate ports, AuthorizedKeysFile redirection
private/etc/pam.d/Added modules — a malicious PAM module captures credentials at every sudo
private/etc/hosts, resolv.confRedirection of update or security domains
usr/local/bin/, usr/local/sbin/Writable despite looking like a system path (§12.3) — shadowing real commands
private/var/db/dslocal/nodes/Default/users/Account records — hidden users, root enabled, added admins (§55)
 
# shell startup files modified after the OS was installed
find /mnt/data/apfs5/Users/*/ -maxdepth 1 \
     \( -name '.zsh*' -o -name '.bash*' -o -name '.profile' \) \
     -printf '%TY-%Tm-%Td %T@ %p\n' | sort -k2 -rn

# anything in the shell files that fetches and executes
grep -nE 'curl|wget|base64|osascript|python|nc |/dev/tcp' \
     /mnt/data/apfs5/Users/*/.z* /mnt/data/apfs5/Users/*/.bash* 2>/dev/null

40The persistence sweep

One pass, in order. Tick them off; do not rely on memory.

Launch and login

  • /Library/LaunchDaemons
  • /Library/LaunchAgents
  • ~/Library/LaunchAgents (every user)
  • /System/Library/Launch* (seal check)
  • /Library/StartupItems
  • BTM BackgroundItems-v*.btm + older versions
  • com.apple.xpc.launchd/disabled*.plist
  • Login/Logout hooks
  • TALAppsToRelaunchAtLogin

Scheduled

  • /var/at/tabs/*
  • /etc/crontab, /var/at/jobs
  • /etc/periodic/* + periodic.conf
  • /etc/emond.d (anomaly on 13+)

Managed

  • Configuration profiles
  • Managed Preferences
  • MDM enrollment state
  • System extensions db.plist
  • KextPolicy, ExecPolicy

Plugin surfaces

  • SecurityAgentPlugins
  • Audio HAL plug-ins
  • QuickLook, Spotlight importers
  • Input Methods, ColorPickers
  • PreferencePanes, Screen Savers
  • Services / Workflows / Folder Actions
  • App bundle XPCServices & PlugIns

Unix

  • Shell rc files, user and system
  • sudoers + sudoers.d
  • authorized_keys, sshd_config
  • pam.d
  • hosts, resolv.conf
  • /usr/local/{bin,sbin}
  • dslocal user records

Cross-checks

  • Repeat the entire sweep inside every snapshot
  • Diff snapshot results against the live volume
  • Every plist's Program exists?
  • Every binary code-signed? (§57)
■ CAUTION — THE SWEEP IS WORTHLESS WITHOUT THE SNAPSHOT PASS

A competent adversary removes their persistence before the machine is imaged. Running this checklist against the live volume alone will then return nothing, and you will report "no persistence identified" about a machine that was comprehensively owned. Run it again inside every snapshot (§42) and diff the results. The difference between the two is the cleanup, and the cleanup is the finding.
